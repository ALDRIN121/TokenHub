# Import performance and browsing improvements

Implemented on `codex/performance-import-progress`. Target is an older 8 GB laptop with an SSD; measurements below are from the development Mac, not a certification of that hardware.

## Results

Deterministic synthetic Codex histories, 100 events per file, fresh TokenHub databases, three aggregate samples and five cached HTTP samples. Workloads use only generated files. Absolute times vary with hardware and load. Before/after imports exclude discovery and approval; those costs are reported separately in the JSON results.

| Events | Import before → after | Persistence before → after | Full analytics before → after | Idle SELECTs before → after |
|---:|---:|---:|---:|---:|
| 1,000 | 0.374 → 0.056 s | 0.330 → 0.035 s | 0.032 → 0.032 s | 13 → 4 |
| 10,000 | 3.549 → 0.483 s | 3.207 → 0.314 s | 0.338 → 0.129 s | 103 → 4 |
| 50,000 | 17.766 → 2.540 s | 16.084 → 1.693 s | 1.793 → 0.661 s | 503 → 4 |

At 50,000 events, the UI summary plus first 25 sessions is 10,572 bytes, versus the previous full response's 929,958 bytes (about 99% less). First uncached summary/page requests were 0.184/0.474 seconds; cached summary plus page took a median 0.0015 seconds. Observed resident memory after the workload was about 114 MB, versus 183 MB previously; this is process RSS, not an isolated allocation measurement. The additional 10,000-event workload exercises all five real parsers and imports all 10,000 events.

## What changed

- Imports run in one managed background worker. Startup serves the UI before importing; progress reads stay available during parser work and uncommitted SQLite batches.
- The progress panel shows discovery, reading, saving, files completed, bytes or records in the current file, elapsed time, and safe outcomes. It reconnects after reload. Active polling is one second; unchanged idle polling is ten seconds, with hidden-tab suspension.
- SQLite writes use batches of 500. Cursors are fetched together. A failed or interrupted source transaction publishes neither partial replacement data nor an advanced cursor. Failed rebuild sources keep their previous imported usage.
- SQL computes totals and groups; only Claude requires global copied-message ranking, before date filtering. Separate read transactions see committed WAL snapshots. Indexes support dates/models/message identity.
- Models, sessions, expanded model details and source health use bounded pages. Page changes replace rows; searches cancel obsolete reads. Date-only changes leave provider discovery/quality alone. Unchanged pages use a 32-entry, 16 MB cache.
- Existing synchronous/full APIs remain available. New UI calls use `background=true`, bounded summaries, and paginated routes. Job history stores at most 50 safe snapshots in an atomically replaced local JSON file, avoiding contention with the SQLite writer.

## Verification and continuing budgets

Regression checks cover accounting parity, unknown/zero counters, metadata enrichment, copied Claude history outside date bounds, pagination/sorting/search, approval/origin/path gates, startup concurrency, job coalescing/recovery, failed history writes, transaction interruption, reload/polling, lazy detail and stale response handling. Deterministic budgets require 25 mounted/fetched rows, under 20 KB for the 10,000-event summary/page, no SQL for cached reads, and fewer than 15 idle SELECTs for 100 sources. They avoid unstable hardware timing assertions except the bounded concurrency checks.

Reproduce with `.venv/bin/python scripts/benchmark_performance.py --events 1000 10000 50000` and `--provider all --events 1000 10000`. Full machine-readable results are in `2026-09-30-benchmarks.json`.

Browser automation could not open the loopback preview in this environment, and Chrome automation was unavailable. Component interaction tests and the production build cover UI behavior; package smoke tests exercise the installed local server and assets. Visual layout on the actual lower-end laptop still needs a manual check.

## Next enhancements

| Priority | Enhancement | Acceptance check |
|---|---|---|
| Next | Pause/resume at committed source boundaries | Shutdown/resume imports exactly the remaining files; no duplicate counts or lost cursors. |
| Next | Export filtered usage and import diagnostics | Exports respect selected dates/providers and contain no paths, prompts, credentials or raw sessions. |
| Later | Trends and period comparisons | Daily totals reconcile with existing accounting, including unknown values and session-total limitations. |
| Later | Incremental aggregate tables for very large histories | Million-event measurements demonstrate a benefit; canonical Claude replacements and rollback remain correct. |

Parsing still retains normalized events for one source so it can commit that source atomically. Exceptionally large single files can therefore use more memory than the ordinary 100-event files in these measurements. Streaming normalized events through a temporary staging table is a future option if single-file workloads demonstrate a need.
